## 最小失联修复的审查与实现

沿用本地既有《阶段 1 最后一轮针对性验收》记录的存活租约候选方向，未采用单纯缩短活动 TTL：

- 每个新 Observer 保留随机实例 ID；后台线程每 2 秒向认证的独立 `/observe/heartbeat/v1` 发送仅含该 ID 的心跳。单次 HTTP 使用原来的 150 ms 超时，不写 MCP stdout；停止等待有界。
- 生命周期载荷增加由传输端赋值的 `leased=true`，MCP 工具参数不允许伪造该字段或 Observer ID。Hook 定义、工具公开 schema、信任和 Token 不变。
- 接收端赋单调时间，不接收客户端时间。10 秒未续租时，其非终态任务转为 `disconnected`，不再计入工作数；控制器发一次受节流的“观察连接失联，任务状态未知（未确认完成）”提示，三语同步。
- 心跳证明 Observer 到 Shion 的可达性，不能证明任务进展、人工授权结果或 MCP 客户端仍在投递。健康连续心跳可覆盖 300 秒活动 TTL，因此无 Hook 的正常长任务不会被凭空判为失联。
- 租约中断后心跳恢复仅转 `uncertain`，不会恢复旧工作/人工等待或产生 Stop。需要新的、非重复活动事件恢复工作；明确 Stop/Interrupt 仍按原语义逐轮结束，结果保持 unknown。
- 尚未升级的 Observer 没有租约能力，仍以 300 秒兜底转“状态未知”，不能仅凭沉默断言其进程死亡。已安装包没有被替换，因此本轮源码修复尚未进入现有安装。
- 队列溢出、过旧队列、容量不足仍保守降级。任务和租约表最多各 1024，逐任务上下文 32、去重身份 2048；墓碑不自动淘汰，饱和后显示未知，避免延迟旧事件复活。

限制：10 秒是健康接收/轮询条件下的逻辑阈值，不是桌面硬实时保证；GUI 卡死或系统暂停会延迟呈现。Observer 仍存活而客户端停止发送 Hook，无法靠心跳识别；在禁止内容读取、又不能把正常静默误判为失联的约束下，不能给出该故障的统一检测时限。恢复原 MCP 连接仍依赖 Codex 客户端，未调用或验证刷新接口；此前新建 CLI 可以恢复的证据仅按原样保留。

## P1～P5 核心

`shion.scheduler.Scheduler` 默认 `enabled=False`，只有显式 `enabled=True` 才处理元数据。生产 `controller/app/bridge/state` 均未导入或实例化它，阶段 1 GUI 仅接入上述租约降级，不使用新仲裁。

| 优先级 | 核心行为 |
| --- | --- |
| P1 | 仅经来源能力声明、可靠 request_id 的人工等待；多请求逐个保留，重复幂等，UI acknowledge 不等于授权/解除 |
| P2 | 可靠最终失败、按连接合并的失联、未知及容量降级；保留全部受影响任务键 |
| P3 | 中性回合结束/中断；每轮一次，2 秒窗口内按品牌与类别合并，独立排队，可确认消除，30 秒过期 |
| P4 | 正常工作；同级前台优先，后台状态持续维护 |
| P5 | 仅显式确认覆盖、没有可信活动/待确认问题/提醒时空闲；启动、沉默和 SessionStart 不能证明全局空闲 |

同级最短展示 1 秒，前台身份稳定 300 ms 后生效；无可靠前台绑定时保留展示并每 5 秒公平轮转。高优先级可以立即抢占，不受同级最短展示限制。前台必须由调用者传入已验证的完整任务键，不按品牌、短 ID 或进程名推测。

请求与事件去重分离；已解除/未知请求保留墓碑，不因延迟重复重新等待；失联或过期撤销可信人工等待声明，重新连接不会恢复该声明。可靠解除只表示请求不再等待，不推断工作恢复。请求表 1024，提醒队列 128；饱和可见降级，不把未接收任务视为空闲。

来源能力默认全关，按 provider/runtime namespace/channel/client surface 独立配置。ChatGPT 当前没有真实可靠请求/解除/最终失败适配器，模拟中的能力声明不代表客户端通过验收。内部保留客户端表面、运行时、来源和 Observer 上下文；界面候选只有 Claude / ChatGPT 两品牌。核心完全没有授权、暂停、继续、中断、发送消息或进程控制接口。现有 Claude RemoteHub 与控制逻辑未改。

## 自动化证据

- 定向观察、租约、调度、离屏 UI 测试：**53 passed**。包括默认关闭、P1～P5、前台迟滞、公平轮转、多请求、不可信权限、客户端能力隔离、终态去重、提醒合并、队列饱和、跨品牌/运行时/会话/轮次隔离、过期和恢复。
- 确定性时钟：仅两个生命周期事件后持续 3600 秒心跳保持工作；9.999 秒有效、10 秒失联；恢复心跳及重复事件不会假装任务完成或重新工作。旧 Observer 300 秒转未知。单个漏拍不误判。
- 独立 stdio/HTTP 子进程：新 Observer 无 Hook 时发送心跳；直接终止测试自己创建的 Observer 后，实际收到的元数据经生产任务表按租约过期，结果 unknown、非终态。这里的到期时间使用模拟时钟，不能冒充桌宠真实故障画面。
- 10 会话、6000 个模拟事件并重复投递：保持 10 个独立活动任务，6000 个重复被去重；逐个结束后归零，无成功结果推断。
- 无心跳合成 HTTP 基线：10 秒、1000 事件、10 会话、零失败；P95 63 ms、最大 93 ms。负载为每秒 100 事件、50 ms 消费周期，非真实 Hook/GUI 延迟。
- 加入 10 个心跳发送者及调度核心：60 秒、6000 生命周期事件及 300 心跳、10 会话，零失败、未降级；队列峰值 17，P95 78 ms、最大 94 ms。与上述 10 秒基线时长不同，仅作描述性对照，不据此宣称真实 Hook 新增开销为固定差值。

- 提交前 `tools/check_private.py`、暂存差异检查通过；本地 Author/Committer 均为项目要求的 noreply 邮箱。未新增依赖。

## 后续正式 GUI 接入风险

需要经过真实客户端能力校验的适配器、前台任务绑定、既有 Claude 单会话字段到逐轮键的映射，以及避免新旧两路重复计数/提醒的迁移方案。还需处理 P1 与已有授权面板/角色交互/气泡优先级的关系、未决请求 UI 可达性及语言文案。以后部署租约修复需协调 Observer 与接收端版本；旧 Observer 接入新接收端使用旧 TTL，新载荷接入旧接收端会被拒收，不能只替换一端后宣称租约生效。独立核心的模拟通过不能证明这些集成已完成。待单独实施和验收后再启用，不把本轮标为阶段 2 全部完成或 V2 可发布。
