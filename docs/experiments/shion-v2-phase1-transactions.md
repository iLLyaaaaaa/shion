# 阶段 1 安装事务可靠性专项

日期：2026-10-28。范围仅为 Windows 文件替换和正常 Hooks 信任变化后的安全卸载。未修改真实用户级配置、ACL 或信任，未安装正式 Hooks；不 push、合并、发布或进入阶段 2。

## 1175 的事实与根因边界

旧提交 `5dc9eda` 的完整日志：`build/preinstall-20261028/pytest-full.log`。结果为 1 failed、1618 passed、9 skipped。具体失败：`test_crash_and_crash_during_recovery[2-uninstall]`。

调用链：`recover()` → `atomic(config.toml, 已安装内容)` → `replace_private()` → `ReplaceFileW(config.toml, .config.toml.shion-stage, NULL, 0, NULL, NULL)`。旧位置分别为 `tools/codex_config.py:400` 和 `shion/observer_files.py:47`。

当时的事务是卸载：日志已经预写，`config.toml` 已还原为卸载后内容，随后模拟崩溃；`hooks.json` 和归属仍在安装状态。恢复准备把 config 恢复到安装状态时，原生 API 返回 1175，**早于测试包装器再次抛出 Crash**。包装器调用 real 后才计数/注入，不持有配置句柄。原实现写入流也在调用 API 前关闭，因此不能把这次错误归咎于故障注入持有写句柄。

旧实现的两个缺陷已确认：没有在严格状态核验后处理可恢复原生失败；失败时 `finally` 无条件删除暂存，会丢掉 1176/1177 场景的重要替换图像。旧失败现场后来重新恢复成功且再次执行为无操作，证明日志仍能恢复已知状态，但不等于旧实现已可靠。

[Microsoft ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)明确区分 1175（两个原文件名保留）、1176（不指定备份时原目标可能消失）、1177（旧文件可能改名、暂存可能已继承属性）。不能把三个错误当成同一状态重试。

本轮真实原生探针（`build/txn-reliability-20261028/native-probe/results.json`）：

| 条件 | 实测 | 文件状态 |
| --- | --- | --- |
| 正常、中文/空格路径 | 替换成功 | 暂存消失，原 DACL 保留 |
| 原目标或暂存被实际 Win32 句柄占用，未共享 DELETE | 错误 32 | 两文件及原 DACL 均保持 |
| 原目标或暂存设置只读属性 | 错误 5 | 两文件及原 DACL 均保持 |

第一轮修正后的四进程压力测试还捕获了一次**真实 1175**：`hooks.json` 路径长 97 字符，原属性为 32（Archive，无只读位），调用前后原文件身份、内容、时间、属性、DACL 和暂存状态均相同；核验后的重试成功，场景未失败。证据：`build/txn-reliability-20261028/stress-final/stress.json`。

这些证据支持一次短暂的系统替换障碍；**无法确定上次或本轮具体是哪个进程、过滤驱动或系统竞争触发了 1175**。没有声称已定位杀毒/索引器，也没有把受控的错误 32 当作原 1175 的进程归因。持久权限/只读/路径问题有独立错误分支，不能靠无条件重试掩盖。

## 最小代码变更与状态规则

`shion/observer_files.py`：原生替换继续使用 flags=0 的 ReplaceFileW，保留已有文件 DACL。有效 ACE 保留，继承标志位可能被 Windows 系统规范化。无忽略错误标志、无非原子覆盖降级。新增状态快照只在内存存在：SHA-256、设备/文件身份、长度、mtime、属性、owner/group/DACL 指纹。没有独立 ACL 存储或权限修复。

最多四次原生调用，退避 10/30/60 ms、250 ms 重试截止预算；每次重新校验全部前置状态。到期、文件变化、读取/权限错误或未知状态立即停止。该预算限制重试等待和是否再发起调用，无法中断 Windows 的同步文件 I/O，不承诺整个事务 250 ms 完成。预期哈希从预览/日志一路传到替换，暂存写完后再检查原文件，避免把暂存期间的外部编辑覆盖掉。

| 失败状态 | 处理 |
| --- | --- |
| 32 / 33 / 1175，原目标和暂存保持已知状态 | 在预算和次数内重新核验后重试 |
| 重试预算耗尽、错误 5 等其他错误 | 抛出失败，不把失败视为成功；保留暂存供日志核验 |
| 1176 / 1177、目标缺失/改名或内容不匹配 | 不重试、不猜测改名文件；保留 WAL/暂存，恢复预检停止 |
| 原文件在预览后、暂存期间或恢复期间被外部改写 | 停止，保留外部内容；事务创建后的哈希不自动接受新编辑 |
| 完整已知暂存、目标为事务已知前/后状态 | 依日志恢复；可重复执行，恢复再次中断后仍按同样规则预检 |
| 部分/陌生/被占用暂存、丢失/损坏/冲突证据 | 停止，保留现场；不因超时删锁或跳过恢复 |

原子替换仍短暂写完整目标配置到同目录暂存。成功后不保留原文副本；异常不明时暂存可能残留供人工处理，这不是长期原配置备份机制。

## 信任兼容与第三方配置保护

`tools/codex_config.py` 的归属及 WAL 更新为 v3：归属保留原插入证据、精确 Shion MCP/Hook 定义、原 JSON 容器/事件存在性；事务保存**本次实际**文件前后 SHA-256 和只属于 Shion 的插入/移除字节。没有原配置全文。未真正全局安装过的 v2 方案不自动迁移；若发现遗留 v2 归属或未恢复日志，必须单独审核。

安装/卸载预览允许官方添加/修改信任记录和第三方追加配置，但必须同时证明：

1. TOML 的原批准片段仍唯一且完整，MCP 定义精确一致。
2. JSON 的每个批准 Hook 仅有一个精确语义匹配；即使第三方重排版 JSON，也只删除对应当前字节范围，正确处理相邻成员的分隔逗号。
3. 删除前后均能解析，且移除 Shion 定义后的其他语义完全相同；比较区分 bool/int 等类型，支持无关 TOML NaN。
4. 生成事务后严格匹配本次前/后哈希；任何新外部编辑停止，不取消哈希校验。

**全部信任记录均保留，包括官方创建的 Shion 信任记录。** 安装器从未拥有这些记录，不擅自启用、禁用或删除它们。其他 MCP、notify、第三方 Hook 的值和语义保持；优先保留原字节，仅删除 Shion 字节范围及必要分隔符。唯一片段/定义被改写、重复、出现未知 Shion 身份或语义不明时停止。

同一命令与目录的重复安装/重新连接为无操作；不同运行路径仍要求另行审核迁移。临时禁用/启用只改变 Observer 自己的凭据 enabled 标记，不改全局配置或信任。卸载后可再次安装和卸载，保留当前第三方数据。
